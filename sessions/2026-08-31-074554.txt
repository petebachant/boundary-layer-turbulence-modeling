⏺ Confirmed it's a real stale answer, not a summarizer bug: the current
  evolution archive's top eight structures use power, inverse, tanh responses —
  no rectifier — so the key honestly reads 0. The archive changed when the
  pipeline was re-run under the new environments (this is the non-reproducing
  evolve-closure stage from roadmap §4), the evidence updated itself, and the
  prose didn't. So the pipeline did its job; the Q&A layer had no mechanism to
  notice.

  My assessment of how to protect against it, in order of how much can be
  deterministic:

  1. Snapshot the evidence when the answer is written (fully deterministic, 
  catches this case).
  An answer is a claim about evidence values at a point in time. Record those
  values alongside it — either inline (evidence[i].value_when_answered: 8) or in
  a lock file (.calkit/questions.lock keyed by question, holding each evidence
  value plus the commit). Then calkit status/calkit check questions compares
  current values to the snapshot and flags "evidence for question 8 changed 
  since the answer was written: evolved_top8_using_rectifier 8 → 0." This is the
  same idea as dvc.lock applied one layer up: the pipeline proves the numbers;
  the lock proves the prose was written against these numbers. It needs a
  tolerance (significant figures, or a per-evidence tolerance:), because a BLAS
  change moving the 13th digit shouldn't invalidate an answer. Re-affirming an
  answer after reviewing it would be calkit questions accept, which rewrites the
  snapshot — the analogue of re-locking.

  2. Render numbers, don't retype them (deterministic, prevents the whole 
  class).
  The paper already does this with \result[key]. Answers could do the same:
  answer: "... {evidence.evolved_top8_using_rectifier} of eight top structures 
  use the rectifier ...", rendered at calkit run/status time. Then a numeric
  claim literally cannot drift; only the qualitative framing can. A weaker but
  zero-migration variant: extract every numeric literal from the answer text and
  require each to match some evidence value to its quoted precision — that
  alone would have flagged "eight"… except it's spelled out, so the rule would
  have to require digits. Rendering is cleaner.

  3. Structural checks (deterministic, cheap, should exist regardless).
  Every evidence.path is a declared pipeline output; every key exists in the
  file; every answered question has at least one evidence entry; no evidence
  path is stale per dvc status. This catches broken links, not wrong prose.

  4. The agent skill (non-deterministic, for what's left).
  After 1–3, what remains is semantic drift: the numbers match but the sentence
  no longer follows from them ("load-bearing" when the ablation gap shrank to
  noise). That's a judgment call and belongs in a skill — calkit:check-questions
  — that reads each question, its evidence values, and the snapshot diff, and
  reports only on questions the deterministic layer flagged or on request.
  Keeping it advisory and out of the pipeline avoids putting an LLM on the
  reproducibility path; the deterministic layer decides whether something needs
  a look, the skill helps decide what to write.

  The main design question for calkit is where the snapshot lives. Inline in
  calkit.yaml is visible and diffs well but bloats the Q&A section; a lock file
  keeps calkit.yaml human-authored and makes "accept" a mechanical operation,
  which I'd lean toward — it mirrors how dvc.lock is already treated in this
  repo.

  If you want, I can prototype layer 1+3 as a project-level check-questions
  stage here (reads calkit.yaml, writes results/question-status.json, fails
  loudly on drift), which would fix this instance and give calkit a worked
  example to absorb.

⏺ Here's how I'd frame it, building on what's already there.

  The abstraction: an injection with a provenance record

  Every piece of a document that came from elsewhere in the project — a number,
  a figure, a table, a text block — is one record:

  {kind, source_path, key?, stage, hash, commit}

  Calkit can produce that record for any path from calkit.yaml + dvc.lock (stage
  graph, output hashes) without the document's help. The document's job is only
  to mark the injection points. Then two things fall out for free: a sidecar
  (paper/main.provenance.json: every injection, where it's used, what it
  resolved to) that tools can read, and a visible marker in the rendered output
  that links the reader back to the source. The format-specific part is just the
  marking syntax and the marker rendering.

  TeX first

  json-to-latex already gives you the right authoring API — \result[XInlet] — so
  keep it and change what it expands to.

  1. calkit.sty, shipped by calkit, with a provenance option. The generated
     generated-numbers.tex defines \result[key] as
     \ckvalue{key}{value}{results/paper-numbers.json}{stage}{md5}. In final mode
     it prints the value, exactly as now. With [provenance], it prints the
     value with a subtle marker (colored underline or a small ⟲) and a hyperref
     link whose target is the artifact's page on the hub
     (https://calkit.io/<owner>/<project>/…#key) or a ck:// URI. Each use also
     \writes a line to a .ckprov file, which calkit folds into the sidecar after
     the build — that gives the reverse trail too: value → every place it
     appears.
  2. Figures and tables: \ckfigure[opts]{figures/dissipation.pdf} wraps
     \includegraphics, and \cktable{results/models.json} renders a table. Their
     provenance comes from a generated calkit-provenance.tex (path → stage →
     inputs → hash), so the caption can carry "produced by stage plot from
     results/energy-flux.json" in provenance mode.
  3. Text blocks, and the questions: a questions-to-latex stage renders each
     question with its placeholders resolved and emits \ckquestion{n},
     \ckanswer{n}, \ckevidence{n} (an automatic evidence list: results, figures,
     publication sections). A "Findings" section in the paper becomes literally
     reactive: re-run the pipeline → numbers update → check questions flags any
     sentence that needs re-reading. Same macro for any stage-produced .tex
     fragment: \ckinput{path}.
  4. Reading the source: the macros are the marker. The VS Code extension
     (already in the repo) can resolve \result[XInlet] on hover from the
     sidecar: current value, source file, stage, last commit that changed it.
  5. Verification: calkit check publication paper/main.tex — every injection
     resolves, every value in the last build's sidecar equals the current
     results, every figure hash matches dvc.lock. Deterministic, and the
     document-side twin of check questions.

  One wrinkle worth fixing on the way: json-to-latex resolves top-level keys
  only, which is why this project has a make-paper-numbers flattening stage.
  Reusing the dotted-key walk from calkit/questions.py there
  (\result[results.temporal-mixing-layer.clip-k-omega-gamma.normalized]) makes
  that stage unnecessary.

  The other formats

  Same record, different markers — and there's precedent for the pattern in
  calkit already (pipeline.sync_markdown):

  - Markdown / MyST / Quarto: a {{ ck:value results/x.json:key }} placeholder
    preprocessed by a stage, or a MyST role / Quarto inline code that reads the
    sidecar; the marker renders as a link.
  - docx: content controls bound to a custom XML part are reactive by
    construction (Word refreshes them from the XML); the XML part is the
    provenance record. pptx: shapes with alt-text carrying the record, refreshed
    by a stage.
  - Every format writes the same sidecar, so calkit check publication and the
    hub's "where is this used?" view are format-agnostic.

⏺ Everything is committed and the pipeline is up to date. Here's what the
  broader search turned up, and what it changes.

  The deterministic lineage (new §7b in docs/learning-closures-lit-review.md)

  The question this project asks was first answered in 1993, with the same data
  class and a much smaller hypothesis space:

  - Rodi & Mansour (1993) fitted $C_\mu$, $f_\mu$ and the $\epsilon$-source
    directly to channel/boundary-layer DNS budgets (Mansour, Kim & Moin 1988).
    Result: every existing $f_\mu$ was wrong near the wall, and the one fitted
    to the data fixed the channel and little else — the in-sample-only result we
    reproduced with a larger library.
  - Durbin (1991) answered the same DNS structurally rather than parametrically:
    $v^2$–$f$ replaces the damping function with a transported stress and an
    elliptic equation. That's the precedent for our rectifier-vs-smooth-term
    finding: in both cases the data rejected the form.
  - Wilcox (1988), Spalart–Allmaras (1992), Spalart (2015): coefficients set by
    analytical constraints (log law, decay, spreading rates), DNS used to
    reject, not to fit — the opposite order from a data fit.
  - Bypass transition specifically: Lardeau, Leschziner & Li (2004) fitted a
    nonlinear EVM to bypass-transition DNS and found the pre-transitional streak
    energy had to be explicit (our ks); Ge, Arolla & Durbin (2014) transported
    intermittency with an onset criterion in $Re_v$ and calibrated the threshold
    — the closest published relative of the clip closure, which makes our
    $\Lambda_c \approx 440$ agreement, not discovery.
  - Bayesian calibration to DNS (Cheung et al. 2011, Oliver & Moser 2011, Ray et
    al. 2014, Edeling et al. 2014) established that model-form error dominates
    coefficient uncertainty — the finding the ML decade then tried to fix.

  The black-box end (§7c)

  The a-posteriori generalization record is now explicit and mostly negative:
  Nishi et al. (2024) found an FIML-augmented model worse than baseline on an
  out-of-class separated flow; Rumsey, Coleman & Wang (2022) at NASA searched
  for any data-driven SA improvement satisfying "universal" and "no harm" and
  found little; Volpiani et al. (2021) similar. The symbolic-regression branch
  (ours) has responded by making the transfer penalty an objective — multi-case
  CFD-driven training (Waschkowski 2022, Fang 2023), conditioned inversion +
  sparse regression (Wu & Zhang 2023, 2025), nonlocal features, embedded
  equation learners, mixture-of-experts (2025–26 arXiv). Spalart (2023) is the
  sharpest rebuttal: edge-of-turbulent-region behavior, free-stream sensitivity,
  invariance and the log law are analytical properties out of reach of

  The ideas log (§7.1, §7.2) records exactly your framing as "not tried", and
  the reasoning there still holds: a momentum-term library is strictly more
  general than the eddy-viscosity ansatz (which is one column of it), and the
  44° stress–strain misalignment we measured pre-transition is the physical
  argument for it — an EVM cannot represent that flow.

  Why I'd do it now, and how

  The reason it stalled was that there was nothing to score it against except
  the calibration case, and §7.1 predicted correctly that it would fit
  beautifully and transfer terribly. The gym removes that objection: the
  objective can be the out-of-sample score from the start. Concretely:

  1. Library. Terms built from what a solver has — U, p, k, ω, ν_t = k/ω and
     their gradients: ∇k, ∇·(ν_t ∇U), ∇·(ν_t (∇U)ᵀ), (k/ω)∇U·∇p, ∇(k)·∇U,
     ω⁻¹∇·(k∇U), etc. Two hard constraints from Spalart's list that the current
     UEqn.H terms violate: Galilean invariance (½|U|² is frame-dependent — the
     term has to go or be rebuilt from gradients) and the edge-of-turbulence
     limit (every term must vanish with k).
  2. Dimensions. Don't leave coefficients dimensional — that guarantees
     non-transfer for a trivial reason (ν differs 4× between the plate and the
     channels). Nondimensionalize each term with local scales (k/ω for time, √k
     for velocity, √k/ω for length) so coefficients are pure numbers; keep a
     dimensional variant as a control to measure how much non-transfer is units.
  3. Search. Bayesian optimization is the right tool here precisely because this
     adds coefficients (§7.2's own conclusion): a cost of (multi-case gym
     score) + (divergence penalty), with stability treated as a feasibility 
     constraint in the BO rather than a term in the loss, so the surrogate
     learns where the solver blows up. BoTorch/Ax or scikit-optimize fit in
     py-compute. Fit on the plate, report on the other seven cases; then fit on
     all eight at once, which is the multi-case training the roadmap already
     lists.
  4. Tiers. Terms with only wall-normal derivatives run in the parabolic solver
     (seconds per evaluation, ~100–300 evaluations for BO); anything with an
     x-derivative breaks the parabolic assumption and goes to OpenFOAM, where a
     BO budget of a few dozen runs is realistic.
  5. Report the posterior, not the optimum. Per-case credible intervals per
     coefficient, and their overlap across cases as the transferability measure
     — the quantitative form of the paper's thesis.

  The one-definition closure (now ideas-log §7.3, roadmap §2.3b)

  Looking across every closure in pypkg/closures.py and sim/newModel/src, a
  transport-equation closure is a small algebra: transported scalars with
  wall/free-stream conditions; per scalar a diffusivity, an explicit source and
  an implicit sink — which is exactly the source_ex/source_im split our
  march_scalar takes and the fvm::Su/fvm::Sp split OpenFOAM's fvScalarMatrix
  takes; a $\nu_t$ expression; and a few non-smooth operators (max, rectifier,
  Heaviside) plus wall distance and strain/rotation invariants. Same algebra on
  both sides, so one spec can compile to both.

  My recommendation: a declarative spec with expressions as strings, parsed once
  by SymPy (dimensional consistency comes free), emitted as a numpy Closure and
  as an OpenFOAM RASModel via a template. That's the OpenSBLI pattern (Lusher &
  Sandham — symbolic equations → generated solver, and the code behind the DNS
  we just added) and the UFL pattern, so the tractability question is settled.
  On TeX: parsing it is the fragile direction — every system that tried ended up
  with a DSL wearing TeX clothing — but the inverse is cheap and gives what you
  actually want: generate the TeX from the spec and inject it into the paper
  through the same provenance machinery as the numbers, so the equations in the
  paper cannot differ from the model that ran. The cross-tier consistency check
  then tests a code generator instead of two hand-written implementations, and a
  fork "changes the model under test" by changing one file.

  What's out there (rans-gym.md §4b)

  - The closest thing is the Closure Challenge (McConkey, Buchanan, Smidt,
    Bodner, Dwight, 2026 — the McConkey of the Kaggle-hosted dataset your issue
    #3 links). Ongoing, field-wide, aimed squarely at Reynolds-number and
    geometry generalization. Submissions are predicted flow fields on given
    meshes for withheld cases (periodic hills, ducts, curved step, NASA hump,
    some 3-D), scored by scaled MAE, with training on test data forbidden and a
    steward updating the leaderboard. The differences from the gym are the
    interesting part: their unit is a prediction by any method, ours is a
    closure run in a common solver with one coefficient set; their hold-out is
    by rule, ours is by each closure's declaration; their score is MAE, ours is
    error over a declared per-case target; theirs is centrally stewarded, ours
    regenerates by forking. Complementary — a closure scored here could be
    submitted there.
  - Surrogate benchmarks — AirfRANS and the NeurIPS 2024 ML4CFD competition,
    PDEBench, CFDBench, The Well — score learned solvers, not closures; good
    precedents for packaging and multi-criteria scoring (ML4CFD also scores cost
    and out-of-distribution robustness).
  - Workshops (NASA TMR, AIAA DPW/HiLift/transition-modeling) are the classical
    human-run benchmark: strong on verification, nothing re-runs when data
    arrive.
  - Kaggle proper: the ClimSim competition is the nearest crowdsourced-closure
    example — and its follow-up found the leaderboard didn't predict
    a-posteriori stability once 90 winning parameterizations were put back in
    the climate model. A Kaggle-style gym needs the solver run inside the
    scoring, which a CSV upload can't do and the harness does.
  - Issue tracker: #1's links (Xiao's PIML code, Callaham's balance models,
    Piu's aPrioriDNS, SpaRTA) are all a-priori tooling — aPrioriDNS is the kind
    of "DNS reader into a common schema" the fork plan wants; #3 is the Kaggle
    dataset; the rest are attachments.

  On your point: agreed, and I've written it into the ideas log as two kinds of 
  entrant, because forcing a field-predictor into a closure's shape gives up
  exactly what ML is good at.

  - A closure supplies a term; the case supplies the solver, mesh and BCs; "a
    posteriori" means the PDE is solved with the term in it and stability is
    part of the score. This is what the gym does today, and the ONNX/PythonFOAM
    route (PythonFOAM embeds an interpreter in the solver, so the same Python
    evaluation as the screening tier runs in-situ — simpler than an ONNX C-API
    binding) is how a learned term gets in.
  - A predictor supplies the fields from a case description; the case supplies
    the description (geometry, Re, inlet profile, BCs — exactly the inputs cases
    already hold) and the evaluation grid; there is no solve. This is what the
    Closure Challenge and ML4CFD score, and what the gym doesn't yet.

  Both are scored on the same declared targets with calibrated_on = training
  set, so the in-/out-of-sample split applies unchanged. Two things worth saying
  now rather than later: geometry generalization is harder for a predictor (a
  model that only sees a global description can't be run on a geometry it never
  saw, and one that sees local features is a closure at the level of a point),
  and a predictor's fields can be checked against the momentum equation on the
  grid — the residual of the equations it didn't solve is the deterministic
  stand-in for "did it converge". Scoring a hundred-airfoil surrogate against an
  eight-coefficient closure on a flow neither was fitted to is the comparison
  nobody has published.
